# EngramDelta

Does a hashed n-gram lookup ([Engram](https://arxiv.org/abs/2601.07372)) protect long-range recall in a
fixed-size delta-rule state ([Gated DeltaNet](https://arxiv.org/abs/2412.06464))? The spec is in
[ENGRAMDELTA_DESIGN.md](ENGRAMDELTA_DESIGN.md). This is a mechanism study on free-tier GPUs: Kaggle 2 × T4,
with synchronous data-parallel training across the two GPUs.

## Layout

```
engramdelta/
  models/    engram.py (port of DeepSeek's demo)  gdn_block.py (GDN, FLA or pure-PyTorch core)
             transformer_block.py  swa.py  linear_attn.py  model.py (all arms from one config)
  data/      mqar.py (MQAR + local clutter)  lm_data.py (FineWeb-Edu windows)
  eval/      mqar_eval.py  state_metrics.py  lm_eval.py
  utils/     dist.py (DDP)  checkpoint.py  run_log.py (immutable results)  hub_sync.py  config.py
  scripts/   train.py  sweep.py  make_manifest.py  budget.py  param_table.py  ddp_check.py  nccl_smoke.py
             bench_kernels.py  prepare_lm_data.py  eval_lm.py  run_state_metrics.py  sync.py  make_plots.py
  analysis.py                  tables + pre-registered rule checks (no interpretation)
configs/     phase0/ phase1/ phase2/ (one YAML per arm)   prereg.yaml (values fixed after Phase 0)
notebooks/   one Kaggle notebook per step (generated by notebooks/build_notebooks.py)
tests/       Phase 0 tests 1-9 + DDP + LM eval + manifest counts
third_party/ vendored reference code (unchanged): DeepSeek engram_demo_v1.py, FLA naive delta rule
results/     immutable JSON per run (written by the runs, never edited)
```

**Files to read line by line** (design rule 7): `engramdelta/models/engram.py`, `engramdelta/data/mqar.py`,
`engramdelta/eval/state_metrics.py`, `tests/`.

## Running on Kaggle

1. Push this repo to GitHub, or upload it as a Kaggle Dataset named `engramdelta-src`.
2. Optional, recommended: create a Hugging Face write token. Add it as the Kaggle Secret `HF_TOKEN`, and set
   `HF_REPO` in the notebooks' first cell. Checkpoints and results then survive killed sessions.
   For a private GitHub repo, also add the secret `GITHUB_TOKEN`.
3. Run the notebooks in order (accelerator **GPU T4 x2**, internet on). Each notebook's header lists its
   inputs, outputs, expected GPU-hours and stop conditions:

| Notebook | Session | GPU-h | What |
|---|---|---|---|
| `00_env_and_kernels` | T4 x2 | 0.75 | NCCL/DDP smoke test, FLA vs PyTorch kernel check + speed, DDP speedup. Picks `GDN_BACKEND` |
| `01_phase0_tests` | T4 x2 | 0.5 | full test suite on GPU, NCCL DDP checks, parameter tables, determinism (E0.3) |
| `02_phase0_known_result` | T4 x2 | 1.75 | E0.4 to E0.6. Proposes N\*, the step budget and the Phase 1 budget. **You fill `configs/prereg.yaml` and commit it** |
| `03_lm_data_prep` | CPU | 0 | tokenizer + FineWeb-Edu shards. Publish the output as the Kaggle Dataset `engramdelta-lmdata` |
| `10_phase1_pilot` | T4 x2 | 1.1 | E1.0a LR pilot, E1.0c lambda check |
| `11_phase1_H1_grid` | T4 x2 | 4.1 | E1.1 |
| `12_phase1_arms` | T4 x2 | 6.5 | E1.2, E1.2r, E1.2l |
| `13_phase1_H4` | T4 x2 | 0.9 | E1.3 |
| `14_phase1_analysis` | CPU | 0 | tables, plots, state metrics, **Gate 1 table: your decision** |
| `20_phase2_train` | T4 x2 | 9.5 | E2.0 to E2.2 (5 LM runs), resumable |
| `21_phase2_eval` | T4 x2 | 0.75 | ppl, position buckets, in-context-copy loss, state occupancy |
| `22_phase2_analysis` | CPU | 0 | tables and plots |

All runs are resumable. Re-running a notebook skips finished runs and continues unfinished ones from their checkpoint.

**Logs and results download.** Every notebook writes its full printed output (with elapsed seconds and the traceback
of any failed cell) to `logs/<notebook>__<UTC start>.log`, and every training run's output to
`results/_logs/<group>/<run_id>.log`. After every cell, `results/` (result JSONs + all logs, no checkpoints) is zipped
into `<notebook>_results.zip` in the notebook's output. Download that zip from the Output tab and unzip it into the
repo with `unzip -n <notebook>_results.zip -d <repo>`.

## Synchronized DDP in one paragraph

`torchrun --nproc_per_node=2` starts one process per T4. DDP broadcasts rank 0's initial weights and
all-reduces the gradients on every backward pass (non-final accumulation micro-steps run under `no_sync()`).
GradScaler checks for inf on the reduced gradients, so both ranks skip the same steps, and clipping sees
identical gradients. Every rank therefore applies the identical update. A checksum guard verifies
this every few hundred steps, and the decision to stop at the time limit is all-reduced. Data streams are seeded
by (seed, rank, step), so ranks never share examples and resuming is exact. Eval is sharded over ranks and summed.
`tests/test_ddp.py` (gloo, CPU) and NB01 (NCCL, T4) check gradient equivalence with single-process training,
parameter sync and exact resume.
